# Masiya Contributions API contract and Rust implementation guide

**Status:** Proposed v1 contract for the planned Rust backend. It is not implemented. The existing [`packages/api-client/openapi.provisional.json`](packages/api-client/openapi.provisional.json) and MSW handlers are a limited development mock, not the server contract. This document covers the intended product in [`build-instructions-guide.md`](build-instructions-guide.md), including screens that the web prototype does not yet implement.

**Audience:** Backend and client engineers. `MUST`, `SHOULD`, and `MAY` express contract requirements, recommendations, and optional behavior. Produce and publish a machine-readable OpenAPI 3.1 document for this contract before integration; the web and mobile clients generate request and response types from that document. Do not treat the examples below as a complete OpenAPI schema. Version incompatible changes with a new API major version. The final OpenAPI file, its examples and contract tests must agree with this document.

## 1. Scope and decisions

- Staff users manage churches, members, projects, pledges, payments, reports and notifications. Members do not sign in in v1. SMS, WhatsApp and passkeys are outside v1; PDF generation is server-side with browser print as a fallback.
- REST over HTTPS, with base path `/api/v1`; all paths below are relative to it. JSON uses `application/json`, UTF-8 and **camelCase**. Do not expose Rust/SQL implementation names as the wire format.
- A deployment has an organization boundary. Every data record belongs to one organization; users have roles scoped to that organization and one or more churches. IDs alone never grant access. The organization is derived from the authenticated session, not accepted from a request body.
- These are proposed defaults where the guide is silent: UUIDs, page-number pagination, a 30-day idempotency window, full weekly/monthly charges for partial calendar periods, and a defined permission matrix below. Confirm product decisions before production, especially cross-church visibility, partial periods, historical voids and simultaneous pledge changes. Do not quietly ship different rules.
- The mock currently differs in paths, schemas, authentication, persistence, and accounting. Migration requires replacing its OpenAPI file and regenerating the client and MSW handlers, not assuming compatibility.

## 2. Wire conventions

| Concern | Contract |
| --- | --- |
| IDs | Lowercase UUID strings. The client generates UUIDs for offline creates. IDs are unique within a resource type and cannot be reassigned, including after deletion. |
| Money | Whole UGX as JSON integers, never floats or formatted strings. Individual amounts and all returned totals must be within JavaScript's safe integer range `0..9007199254740991`; validate checked arithmetic and reject overflow. Payment/pledge amounts are strictly positive; targets and balances may be zero. No negative money field: state whether a value is `debt`, `advance`, or `unallocatedCredit`. |
| Dates | `YYYY-MM-DD`, a real calendar date in `Africa/Kampala`. An `asOf` date means the end of that Kampala calendar day for event inclusion, while a period ending on `asOf` is due today and not yet overdue. Weeks are Monday through Sunday. |
| Instants | RFC 3339 UTC strings, e.g. `2026-11-09T07:15:00Z`. Persist instants and date-only values separately. No implicit browser-local timezone. |
| Enums | Lowercase `snake_case`, enumerated in OpenAPI. Unknown input is a validation error. Clients must tolerate newly added response fields. |
| Nulls | Required-but-empty optional values are `null` in responses. In PATCH, an omitted field is unchanged and an explicit `null` clears a nullable field. Reject unknown or read-only request fields. |
| Lists | `GET` list responses are `{ "data": [...], "meta": { "page": 1, "pageSize": 25, "total": 123, "totalPages": 5 } }`. `page` starts at 1; `pageSize` defaults to 25, max 100. Empty results are `[]`, with `totalPages: 0`. Stable ordering always adds `id` as a tie-breaker. Search uses `q`, trimmed, case-insensitive, with a max of 100 characters. |
| Sort | `sort=field` or `sort=-field` for descending. Each endpoint below declares allowed fields. Invalid filters, sorts or page sizes return 422, rather than being ignored. |
| Range | `from` and `to` are inclusive Kampala date-only bounds; reject `from > to`. A missing range uses the endpoint's stated default. |
| Caching | Financial and personal responses use `Cache-Control: private, no-store`. `ETag` is an opaque **strong** version token for conditional writes, not permission to store data in a shared cache. The client may keep its own protected offline cache under its data policy. |
| Version | Versioned business-resource reads and mutations include the current strong `ETag`; editable resources also have integer `version` in JSON. Authentication and health responses do not use resource ETags. Conditional writes send `If-Match: "<etag>"`. Require it on versioned business-resource edits, state transitions, relation changes and deletes; missing is 428, stale is 412. Authentication/session actions and push subscription revocation do not use `If-Match`. Offline clients present 412 as a conflict, just as they do 409. |

Except where an endpoint gives a composite or revocation response, successful item reads and writes return `{ "data": <resource> }`, unless specified as `204`, a binary response or a special envelope. A create returns `201`, `Location` and `ETag`. Successful reads and state transitions return `200`; relation changes may return `204` as specified. Deleting a member, church or project returns `200 {data:{id,deletedAt,version}}` and its tombstone `ETag`; authorized `GET /{resource}/{id}/tombstone` returns the same shape and ETag so it can be restored. A tombstone is never a financial record deletion. Other DELETE operations use their explicitly stated response. `GET /health` is unauthenticated, returns `200 {"status":"ok"}` only when the API can serve requests; it must not disclose infrastructure details. A separate private readiness check can probe dependencies.

### Errors

Use `application/problem+json` for every error, with stable machine-readable `code` and a safe message; never include stack traces, SQL, secrets or unnecessary personal data.

```json
{
  "type": "https://api.example.org/problems/validation_error",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_error",
  "detail": "One or more fields are invalid.",
  "requestId": "d1b30f81-540a-4cc3-81d4-7a9bce6f5d34",
  "errors": [{ "field": "/amount", "code": "positive_integer_required", "message": "Enter a positive whole number of shillings." }]
}
```

`field` is a JSON Pointer such as `/amount` (or a query parameter name for query errors); `errors` is present on validation failures. Use 400 for malformed JSON/headers, 401 for missing or expired authentication, 403 for authenticated but forbidden operations, 404 for absent or intentionally concealed records, 409 for a domain conflict or reused idempotency key with different input, 412 for stale `If-Match`, 415 for unsupported media, 422 for valid JSON with invalid fields/business input, 428 for missing required `If-Match`, 429 for rate limiting and 5xx for transient server failures. Send `Retry-After` on 429 and when appropriate on 503. A 408, 429 or 5xx can be retried using the same idempotency key; other 4xx must not be retried automatically. A 409/412 conflict response includes a non-sensitive `current` resource and `currentEtag` only if the user is currently authorized to read it; otherwise omit both. `code` distinguishes `idempotency_key_reused`, `invalid_state`, `reference_conflict`, `stale_version` and `validation_error`.

## 3. Authentication, security and authorization

### Sessions and CSRF

Use an opaque server-side session in a `Secure`, `HttpOnly`, appropriately scoped cookie; use `SameSite=Lax` for a same-site deployment. Prefer hosting the API on the same origin as the web app (or a same-site reverse proxy). If a cross-site deployment is deliberately required, document exact allowed origins, credentialed CORS, `SameSite=None; Secure`, and a CSRF design that does not rely on SameSite. Never use wildcard origins with credentials. HTTPS is required outside local development.

For cookie-authenticated unsafe methods, require an unpredictable session-bound CSRF token in `X-CSRF-Token`, returned by `GET /auth/csrf`, and validate `Origin` against the allowlist. Rotate it on login and session renewal; reject invalid tokens with 403 `csrf_invalid`. Do not put session tokens or PINs in localStorage. Rate-limit login, password reset and unlock by account and network; use generic failure messages and never reveal whether an account exists. Hash passwords with a current, configured password-hashing algorithm such as Argon2id, with unique salts and parameters suitable for the deployment. Never log passwords, PINs, reset tokens, session cookies or push subscription keys.

| Method and path | Auth | Request and response |
| --- | --- | --- |
| `GET /auth/csrf` | Anonymous or session | `200 {"data":{"csrfToken":"..."}}`; no-store. The anonymous token is bound to an anonymous HttpOnly cookie and protects login and reset requests; rotate both on session change. |
| `POST /auth/login` | Anonymous + CSRF | `{phone,password}`; on success set session cookie, return `{data:{user,session,csrfToken}}`; rotate session identifier. `user` is `UserProfile` below. |
| `POST /auth/logout` | Session + CSRF | Revoke current session and its associated push subscriptions, expire cookie; `204`. If no session exists, return `204` without exposing account state; the browser still supplies the anonymous CSRF token and allowed Origin. |
| `GET /auth/session` | Session | `{data:{user,session,csrfToken}}`, including roles and authorized churches. |
| `POST /admin-users` | Organization admin + CSRF | `{name,phone,password}`; create another organization administrator in the same organization, return `201` with user metadata and no password. Phone must be unique across all users. |
| `POST /auth/forgot-password` | Anonymous + CSRF | `{phone}`; always `202` with a generic response. Issue an expiring, single-use reset code through a configured SMS transport when recovery is implemented. |
| `POST /auth/reset-password` | Anonymous + CSRF | `{token,newPassword}`; `204`; consume token atomically, revoke existing sessions and subscriptions. |
| `POST /auth/unlock` | Session + CSRF | `{method:"password"|"pin",credential}`; `204` after server verification. This re-authenticates an existing session; the client lock overlay alone is not a server-side access-control boundary. Apply rate limits and audit failures without credentials. |
| `PUT /auth/pin` | Session + CSRF | `{currentPassword,newPin}`; `204`. Hash the PIN with a per-user salt and a deliberately expensive password hash; rate-limit verification. `DELETE /auth/pin` takes `{currentPassword}` and disables it. |
| `PUT /auth/password` | Session + CSRF | `{currentPassword,newPassword}`; `204`; rotate the current session, revoke other sessions and subscriptions, and return a fresh CSRF token via `GET /auth/csrf`. |
| `GET /auth/sessions` | Session | List the user's sessions (`id`, `createdAt`, `lastSeenAt`, `deviceLabel`, `current`); no token values. |
| `DELETE /auth/sessions/{sessionId}` | Session + CSRF | Revoke an owned session and its subscriptions; `204`. Deleting the current session logs it out. |

### Roles and church scope

Proposed roles are `organization_admin`, `church_admin`, `treasurer`, and `viewer`. `organization_admin` has organization-wide access. Each other role has explicit church assignments. An administrator manages records within their assigned scope; a treasurer reads and manages pledges and payments in scope, but cannot manage user access or delete churches/projects; a viewer reads only. Profile, preferences, sessions, notification actions and subscriptions are always limited to the authenticated user. All sensitive operations are enforced on the server, regardless of UI visibility.

A non-organization admin can access a member when their home church or an active attached church is assigned to that user. A project is in scope when its owner or an active attached church is assigned. A church itself is in scope only when assigned. A project-restricted payment or pledge is accessible only when **both** its member and its project are in scope. An unrestricted payment is readable only when the member and every project touched by its allocations are in scope. Creation or voiding of an unrestricted payment requires access to all pledges whose allocations may be affected; otherwise reject with a generic 403. Member balances for a partially scoped user include only authorized pledges and their allocations, clearly labeled as scoped; do not include unrestricted credit or full payment amounts that would expose out-of-scope activity. For a cross-church attachment, require authority over both endpoints; otherwise return 403 without changing either. This conservative rule is an assumption to confirm for shared projects. Scope **every** query, report, autocomplete, export, notification, sync event and aggregate before computing totals, counts and pagination; never leak out-of-scope data through totals, 404/403 differences or search. The implemented `POST /admin-users` is limited to `organization_admin` and is audited. Future user assignment management is proposed through `GET /users`, `GET/PATCH /users/{id}` and `PUT /users/{id}/church-access` with `{role,churchIds}`; assignment changes must also be audited. `GET /users` is paginated with `q`, `status` and sort `name|phone|createdAt`. User responses contain `{id,name,phone,role,churchIds,status,createdAt,updatedAt,version}`, where status is `invited|active|disabled`. Future PATCH accepts `name`, `phone`, `status` only. Future `PUT` replaces role and church access with a current `If-Match`. Delivery and account acceptance details must be specified before adding other user roles. Disabling a user revokes sessions.

## 4. Resource model

The following is the minimum response shape; resource properties below are required unless marked nullable (request fields have their own endpoint rules); common fields apply to Church, Member, Project, Pledge, Payment, and PaymentAllocation. Notification, UserProfile and AuditLog use their explicitly listed fields and do not implicitly inherit common fields. Use full schemas, constraints, enums and examples in OpenAPI. `id`, `createdAt`, `updatedAt` and `version` are server-managed except client-generated `id` on creates. The server ignores no unauthorized fields: it rejects them. All timestamps and actor IDs in audit data are server assigned. `version` advances on changes that affect the resource or its relations. Names are trimmed nonempty strings, max 200 characters; notes are nullable strings max 2000. User and member phone values are required E.164 strings (e.g. `+256700000000`); church phone values are nullable. `status` names are exact enum values below.

| Resource | Fields beyond common fields | Invariants |
| --- | --- | --- |
| `Church` | `name`, `phone` (nullable), `status: active\|archived`, `memberCount`, `projectCount` | Counts are authorized and current. |
| `Member` | `name`, `phone` (required), `homeChurchId`, `status: active\|archived`, `churchIds`, `projectIds`, `totalGiven`, `debt`, `dueToday`, `advance`, `unallocatedCredit` | Exactly one active home church; home church is included in `churchIds`. Totals are calculated; never accepted as input. |
| `Project` | `name`, `description` (nullable), `ownerChurchId`, `target`, `startDate`, `endDate` (nullable), `status: active\|archived`, `churchIds`, `memberCount`, `collected`, `debt`, `dueToday`, `advance`, `targetProgressBasisPoints` | Owner is always included in `churchIds`. Progress is `floor(collected * 10000 / target)` when target > 0, otherwise `null`; it may exceed 10000. Use checked wide intermediate arithmetic and reject a result exceeding the safe-integer cap. |
| `Pledge` | `memberId`, `projectId`, `frequency: daily\|weekly\|monthly`, `startDate`, `endDate` (nullable), `status: active\|paused\|cancelled`, `versions` (`id`, `amount`, `effectiveFrom`, `createdAt`), `demand`, `paid`, `debt`, `dueToday`, `advance` | Amount is a positive integer. Relationships carry `id`, both endpoint IDs, `createdAt`, `createdBy`, `version`, and nullable `detachedAt`. A `ProjectMember` belongs to a project and member; it is independent of the member's home church. Detaching a relation does not delete historical payments or pledges. Reject detach if it would break an active pledge; cancel or transfer it first. The owner church and home church cannot be detached without first changing ownership/home church. Enforce unique active relationships and foreign keys within the same organization.

## 5. Accounting contract

The server is authoritative for demand, allocation, debt, due today, advance, credit, summaries and statements. `packages/domain` is a TypeScript preview, not a Rust library. Rust cannot import that package directly: implement the rules in a pure Rust domain crate and maintain shared, language-neutral JSON golden vectors in both projects. Compare Rust and TypeScript results in CI. The server response always wins over a preview. Do not represent preview estimates as saved allocations.

### Periods and balances

- Daily periods are calendar days; weekly periods end Sunday; monthly periods end on the last calendar day of the month. The first period starts on the pledge start date; later periods start immediately after the previous end. A pledge ending mid-period ends that last period on its end date. A partial weekly/monthly period is charged the full fixed amount (proposed rule, no proration). `endDate` is inclusive.
- A period ending **before** `asOf` with a remaining balance is debt. A period ending **on** `asOf` is due today, not overdue. A paid amount in a period ending on or after `asOf` is advance, including today's paid daily pledge. Demand is the sum of periods whose start is on or before `asOf`, including a current weekly or monthly period; paid is the allocated amount in those periods using payments dated on or before `asOf`. Unallocated credit is kept separate from advance.
- Persist state transitions and effective dates. Proposed v1: `pause` effective date is inclusive and stops generating periods whose start is on or after it; `resume` is inclusive and starts a new period at the resume date. `cancel` is inclusive as the final date of demand; it is terminal. Reject a transition that would split an existing period unless its date is the period boundary. Changing amount creates an immutable version effective at a period start; reject overlapping versions or a date before pledge start/after end. Historical transitions must recalculate affected allocations in the same transaction and be audited. These lifecycle rules require product confirmation and must be reflected in shared vectors before use.
- Pledge dates and amounts are never retroactively overwritten. A history query exposes versions and pause/resume/cancel events. If state changes create a historical gap, do not count demand for the gap. For a weekly pledge whose current period ends Sunday 11 January, pause and amount changes can first take effect Monday 12 January; cancel may take effect Sunday 11 January. Resume during a gap starts a new partial period on its inclusive date. The present TypeScript preview does not implement lifecycle history, so extend it before claiming full parity. Generate future periods only as needed to allocate funds and within pledge end/status constraints; avoid unbounded enumeration.

### Allocation and immutable payments

For an `asOf` calculation, exclude payments dated after `asOf`. Rebuild allocations deterministically in payment `date`, then payment `id` order. For each eligible payment, consider that member's eligible pledge periods in `periodEnd`, `periodStart`, then `pledgeId` order. A project-specific payment only pays that project's periods; an unrestricted payment can pay all eligible projects. Fill each oldest unpaid period, including partially paid periods, before moving to future periods. An excess with no eligible period becomes unallocated credit. Do not silently spend project-restricted credit on another project. A later backdated payment, pledge change, or void can alter subsequent allocations; calculate and persist the new allocation set and balances atomically.

A payment is never edited or deleted. `POST /payments/{id}/void` requires a reason, records the void actor and instant, and reallocates other payments in the same transaction. Create a replacement as a new payment with its own ID and idempotency key. Define two historical views explicitly: default **current knowledge**, which excludes a payment that is now voided even for an earlier `asOf`; a future `knownAt` instant could give **as known then**, including the payment until its `voidedAt`. V1 does not implement `knownAt` on any endpoint; if supplied, return 422 `unsupported_parameter`. A `knownAt` view must use audit/event history for all relevant changes, not just voids; until full bitemporal history exists, reject `knownAt` with a documented `422` rather than return misleading results. The TypeScript preview only supports current knowledge and cannot reconstruct past void state.

Serialize mutations affecting the same member's allocations with a database transaction and appropriate row/advisory locking or equivalent serializable concurrency. A successful response reflects the committed ledger. Concurrent writes, retries, crashes and rollback must never duplicate money, create a partially updated ledger or lose credit.

**Acceptance vector:** A 1,000 UGX daily pledge starts 1 January 2026. On 11 January, ten completed days are unpaid: debt 10,000, due today 1,000. A 15,000 payment dated 11 January yields debt 0, due today 0, advance 5,000 (today plus four later days), credit 0. Voiding it restores debt 10,000 and due today 1,000. Also test partial payment, project restriction, equal-date tie-breaks, weekly/monthly and partial periods, overlapping pledges, end dates, pause/resume/version boundaries, excess credit, backdated and future payments, historical void behavior, overflow and concurrent writes.

## 6. Idempotency, offline sync and concurrency

Every authenticated business mutation, including action POSTs, PATCH, PUT and DELETE, sends `Idempotency-Key: <UUID>` generated once per logical operation. Authentication, session, PIN and password operations are not offline-queueable and are exempt from idempotency keys; they have their own single-use or session revocation semantics. The read-only payment preview and snapshot creation are also exempt. Create bodies also contain a client-generated resource `id`; these IDs and the idempotency key are distinct concepts. Persist a request fingerprint (method, concrete path including resource IDs, semantic query parameters, `If-Match`, authenticated organization/user and canonical body), response status, relevant headers and response body atomically with the domain write. Scope keys to organization and user. Exclude cookies and rotating CSRF tokens from fingerprints, refresh CSRF on reconnect, and never store credentials or secret response headers such as `Set-Cookie` in replay records. Avatar upload uses the same key with a bounded content digest; do not persist its raw upload in the idempotency record. A retry with the same key and fingerprint returns the original response, including the original `Location` and `ETag`, without reapplying the operation; same key with a different fingerprint returns 409 `idempotency_key_reused`. Reauthorize every retry before returning data. Concurrent duplicate requests must have one effect; wait for the first or return a retryable 503 while it completes. Document a 30-day retention window and tell clients not to automatically retry after it expires; resource IDs and database uniqueness remain a second defense for creates. For non-create operations after the window, refresh state and ask the user before issuing a new logical operation.

`If-Match` and idempotency solve different problems. For an accepted retry, check the idempotency record before re-evaluating the stale precondition, after authentication and authorization. New operations with stale versions receive 412; domain collisions receive 409. On conflict, the client can reload, compare, then submit a new operation with a new key and current ETag. Never replay an expired session's queued mutations under another user.

`GET /sync/changes?cursor=<opaque>&limit=100` returns `{data:[{sequence,entityType,entityId,operation:"upsert"|"delete"|"access_revoked",version,changedAt,resource}],meta:{nextCursor,hasMore}}`; `resource` is null for tombstones. The cursor is opaque, user- and organization-bound, and ordered by a durable change sequence. Each call is authorized using **current** access. Changes to permissions must generate a scoped `access_revoked` tombstone for cached records; if safe per-record revocation cannot be guaranteed, invalidate the cursor and require a full cache purge and resnapshot. Never send previously visible content after access is revoked. Return 410 `sync_cursor_expired` when a cursor has expired (retention at least 30 days); the client clears affected cached data and performs a fresh authorized snapshot. Bootstrap with `POST /sync/snapshots` (empty body): return `201 {data:{snapshotId,expiresAt,changesCursor}}`. Then page through `GET /sync/snapshots/{snapshotId}/items?cursor=<opaque>&limit=100`, returning `{data:[{entityType,entityId,version,resource}],meta:{nextCursor,hasMore}}`. The snapshot is a consistent, scoped view at a durable watermark; `changesCursor` begins strictly after that watermark so commits while paging are replayed by `/sync/changes`. Snapshots and their pagination cursors are bound to user and organization and expire after 24 hours; the change-feed cursor has the separate 30-day retention above. Reauthorize each page; if scope changes invalidate the snapshot and return 410 `sync_cursor_expired` without returning its remaining contents. Clients purge cached data and restart. Define snapshot isolation and test concurrent commits in OpenAPI and integration tests. A server cannot remotely erase an offline device: require a documented client cache expiry and local encryption/key protection appropriate to the deployment, and purge on next authenticated contact, logout or detected permission change. Offline queues remain client-owned; the API accepts normal endpoints and does not need a separate batch mutation endpoint.

For member, church and project records, archive and delete are reversible soft state changes. Session and push-subscription DELETEs are revocations rather than soft deletes; saved-filter DELETE is permanent and does not apply to financial records. Delete returns a tombstone and a new version, and `POST /{resource}/{id}/restore` accepts `If-Match` against the tombstone version and a new idempotency key. Restore is allowed after the client's five-second Undo toast as well, subject to authorization and referential constraints. Deletion must not cascade into financial history; return 409 `reference_conflict` for records required by financial history. Archive and restore update related list counts and change feed. The UI must not offer delete on immutable payments.

## 7. Endpoint inventory

Every endpoint inherits authentication, authorization, paging, errors, CSRF, idempotency and concurrency above unless explicitly exempt. `GET` filters listed below are optional. `asOf` defaults to today's Kampala date. For list rows, calculated money and counts are scoped to the user and the specified `asOf`. Detail responses contain the resource from section 4; use subresources for large child collections, not unbounded nested lists.

### Statements and reports

A statement is a current-knowledge ledger snapshot. `GET /members/{id}/statement` accepts `from`, `to` and `asOf` with `from <= to <= asOf <= today`; the default range is the current Kampala month to today. Return `{data:[StatementRow...],meta:{page,pageSize,total,totalPages,snapshotId,openingNet,closingNet,summary,asOf}}`. The first page creates a short-lived, user-bound `snapshotId`; subsequent pages and export pass it as `snapshotId` so concurrent writes cannot change pagination or running balances. Reauthorize each request and return 410 on expiry or access change. The summary has `{debt,dueToday,advance,unallocatedCredit}` calculated from the same authorized ledger at `asOf` and is not derived from a single net number.

Each row is a tagged union with `type: period|payment`, `date`, `id`, and `netAfter: {kind: debit|credit|zero,amount}` (nonnegative integer). A `period` row also has `pledgeId`, `projectId`, `periodStart`, `periodEnd`, `demand`, `paid` (allocated to that period by the snapshot); a `payment` row has `paymentId`, `amount`, `allocations` and `unallocatedCredit`. Replay all current-knowledge, non-voided payment events and period-demand events effective through `to` in date order, period before payment on a shared date, then type-specific ID. Period demand is posted at `periodEnd`; payment amount is posted at payment `date`. Starting at zero, subtract demand and add payment using checked signed internal arithmetic; represent the resulting absolute amount and sign via `netAfter`. `openingNet` is the replayed net before `from` and `closingNet` is the net after `to`; carry the actual running value across pages. This net is an accounting presentation, not overdue debt: it can include today's demand and credits, and project-restricted funds can coexist with debt elsewhere. Separately show voided payments as audit annotations with original date, `voidedAt` and reason, excluded from the running events and active totals. `paid` on a historical period row reflects allocations at the snapshot and can include a later payment through `asOf`; label it accordingly.

Example: on 11 January, the daily 1,000 pledge and 15,000 payment in section 5 have an opening debit of 10,000 on 10 January; post 1,000 demand then 15,000 payment to close with a 4,000 credit net. The snapshot summary separately reports debt 0, due today 0 and advance 5,000 because 1,000 of the payment covers today's demand. The statement and export must use the same snapshot, filter and authorization. For project filtering, include only that project's demand and allocations; do not attribute unrestricted unallocated credit to a project. This filtered view requires a complete, authorized projection and must explain that its net is allocation-based rather than cash-based.

## 8. Rust implementation guidance

1. Keep HTTP handlers thin. Separate transport DTOs, authorization, application services, pure domain accounting, persistence, and delivery adapters. Use strongly typed IDs, enums and date-only values; reject invalid input at the boundary. An `i64` or `u64` alone is insufficient validation: enforce the JSON safe-integer cap and checked arithmetic on every sum and product. Avoid floating-point money and currency formatting in the server.
2. Use a relational database with transactions, foreign keys, tenant-scoped indexes, unique active relations, unique idempotency keys and immutable audit/event records. Store Kampala dates as SQL `DATE`, instants as UTC timestamps. Make payment creation/void, allocation replacement, balance updates, audit entry, change-feed entry and idempotency result one atomic commit. A transactional outbox should send notifications only after commit; consumers must be idempotent.
3. Choose a maintained Rust web framework and OpenAPI tooling appropriate to the team; the contract is framework-independent. Generate or validate OpenAPI from the same DTOs and handlers, and validate it in CI. Pin dependencies and use security updates. Publish the versioned schema at `/api/v1/openapi.json`; generate the TypeScript client from that artifact and run mock/client contract tests against it.
4. Enforce access in every database query and aggregate, not only route middleware. Recheck membership/role on idempotent replay, export download and sync. Do not trust a client-provided organization, balance, role or allocation. Use parameterized queries, bounded list sizes, upload limits, request timeouts and structured, redacted logs with a request ID.
5. Use database migrations, durable backups and restoration drills. Recalculation must be deterministic and recoverable. Instrument latency, errors, allocation failures and queue lag without logging personal data. Do not return infrastructure diagnostics on the public health endpoint.
6. Default web authentication to secure cookies and CSRF as above. If a native mobile client later needs a different authentication mechanism, define it explicitly in a revised OpenAPI security scheme rather than exposing browser cookies or localStorage tokens as a shortcut.

## 9. Acceptance and delivery checklist

- Publish OpenAPI with every path, parameter, body, response, error, security scheme, conditional header, idempotency rule, and example in this document. Generate client types and update MSW to the same contract; remove provisional assumptions only when the server contract is agreed.
- Run shared JSON accounting vectors against both Rust and TypeScript, including the 10-day/15,000 example, partial and restricted payments, weekly/monthly periods, pledge end, pause, resume, version, void, backdated/future payments, ties, credits, overflow and history. Add property tests for conservation of funds and deterministic replay.
- Contract-test all endpoints and error responses. Test missing/stale `If-Match`, idempotency replay and mismatch, concurrent duplicates, transactional failure, 409/412 conflict presentation, offline retries, cursor expiration and permission revocation. Confirm no records or aggregates leak across church/organization boundaries.
- Exercise login, CSRF, session expiry/revocation, unlock rate limits, password reset, notification actions, scoped push subscription removal, report/statement reconciliation, safe CSV output and PDF authorization.
- Test the intended end-to-end flow: add member and daily pledge, record 15,000 after ten missed days, verify debt 0 and advance 5,000, void and verify debt returns, soft-delete an eligible row and undo, open a notification, and lock/unlock. Test the same payment retry after a simulated network failure and confirm exactly one committed payment.
- Before production, decide the open assumptions in sections 1, 3 and 5, resolve any differences with the mobile product, and document migration from the provisional mock. Do not use the prototype demo as financial data.
